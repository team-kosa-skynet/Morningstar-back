# 1. Java 문법 되짚기

## 1-1. 접근 제어자 — `public` / `protected` / `private`

| 제어자 | 접근 가능 범위 |
|---|---|
| `public` | 어디서든 |
| `protected` | 같은 패키지 + **상속받은 자식 클래스** |
| (없음, package-private) | 같은 패키지 안에서만 |
| `private` | **같은 클래스 안에서만** |

지금은 "정보 은닉"이라는 교과서 설명보다 **훨씬 중요한 사실**이 있습니다:

> **`private` 메서드는 자식 클래스가 오버라이드할 수 없습니다.**
> 그리고 Spring의 `@Transactional`·`@Async`·`@Cacheable`은 **오버라이드로 동작합니다.**
> 그래서 **`private` 메서드에 붙인 `@Transactional`은 아무 일도 하지 않습니다.**

왜 그런지는 [4-4. 프록시](#4-4-프록시--spring-마법의-정체)에서 설명합니다.
이 프로젝트에는 이 실수가 4곳 있습니다 (`PointService`, `Gemini/Openai/ClaudeQuestionService`).

## 1-2. `static` — 클래스에 붙는 것 vs 객체에 붙는 것

```java
public class JwtKey {
    private static Dotenv dotenv = Dotenv.load();     // static: 클래스당 1개
    private static final String JWT_SECRET_KEY1 = dotenv.get("JWT_SECRET_KEY1");
}
```

- `static` 필드는 **인스턴스가 아니라 클래스에 소속**됩니다. 객체를 100개 만들어도 값은 하나입니다.
- `static` 필드 초기화는 **클래스가 처음 로딩되는 순간 딱 한 번** 실행됩니다.
  이걸 *static 초기화*라고 하며, 여기서 예외가 터지면 `ExceptionInInitializerError`가 나면서
  **애플리케이션이 그 클래스를 아예 못 쓰게 됩니다.**
- `final`은 "한 번 대입하면 재대입 불가"입니다. `static final`은 관례적으로 대문자 상수명을 씁니다.

> **이 프로젝트에서**: `JwtKey`, `S3Config`, `EmailConfig`, `RecruitmentService`가 모두
> `static Dotenv dotenv = Dotenv.load();`를 씁니다. `.env` 파일이 없으면 클래스 로딩 시점에
> 죽습니다. Spring의 설정 주입(`@Value`)을 쓰면 피할 수 있는 위험입니다. → [global 문서 참조](global.md)

## 1-3. 제네릭 `<T>` — 타입을 나중에 정하기

```java
public class ResponseDTO<T> {     // T는 "아직 안 정한 타입"이라는 자리표시자
    private final T data;

    public static <T> ResponseDTO<T> okWithData(T data) { ... }
}
```

사용할 때 T가 확정됩니다.

```java
ResponseDTO<Page<BoardListResponseDto>>   // data는 Page<BoardListResponseDto>
ResponseDTO<Void>                          // data 없음 (Void = "값 없음" 타입)
```

제네릭이 없으면 API 응답 껍데기를 응답 종류마다 새로 만들어야 합니다.
제네릭 덕분에 **껍데기 하나로 모든 응답을 감쌀 수** 있습니다.

**타입 소거(Type Erasure)**: 제네릭 정보는 컴파일 후 사라집니다. 그래서 런타임에 `T`가 뭔지 알 수 없고,
캐시에서 꺼낼 때 아래처럼 억지 캐스팅 + 경고 억제가 필요해집니다.

```java
@SuppressWarnings("unchecked")
PageResponse<BoardListResponseDto> cachedPage =
    (PageResponse<BoardListResponseDto>) redisTemplate.opsForValue().get(cacheKey);
```

## 1-4. `record` — DTO 전용 문법 (Java 16+)

이 프로젝트의 DTO 대부분이 `record`입니다.

```java
public record LoginRequestDto(String email, String password) { }
```

이 한 줄이 아래를 자동 생성합니다:

- `private final` 필드 2개
- 생성자 `LoginRequestDto(String, String)`
- **getter — 단, 이름이 `getEmail()`이 아니라 `email()`입니다**
- `equals()`, `hashCode()`, `toString()`

그래서 이 프로젝트 코드에 `dto.email()`처럼 `get` 없는 호출이 보이면 record입니다.

| | `class` | `record` |
|---|---|---|
| 불변성 | 직접 `final` 관리 | 기본적으로 불변 |
| getter | 직접/Lombok | `필드명()` 자동 |
| 상속 | 가능 | **불가** (final) |
| 엔티티로 사용 | 가능 | **불가** (JPA는 기본 생성자·가변 필드 필요) |

→ **DTO는 record, 엔티티는 class**. 이 프로젝트가 정확히 그렇게 하고 있습니다.

## 1-5. `enum` — 상수의 집합, 그런데 메서드도 가진다

```java
@Getter
public enum ErrorCode {
    USER_NOT_FOUND(HttpStatus.BAD_REQUEST, "존재하지 않는 회원입니다."),
    BOARD_NOT_FOUND(HttpStatus.BAD_REQUEST, "해당 게시글을 찾을 수 없습니다.");

    private final HttpStatus httpStatus;
    private final String message;

    ErrorCode(HttpStatus httpStatus, String message) {  // enum 생성자는 항상 private
        this.httpStatus = httpStatus;
        this.message = message;
    }
}
```

Java의 enum은 단순 상수가 아니라 **필드와 메서드를 가진 완전한 클래스**입니다.
그래서 "에러 코드 + HTTP 상태 + 사용자 메시지"를 한 덩어리로 묶어 관리할 수 있습니다.

이 프로젝트의 enum들: `ErrorCode`, `PointType`, `TierType`, `BoardCategory`, `ModerationStatus`,
`MessageRole`, `InterviewMode`, `InterviewStatus`, `JobRole`, `AiProvider`, `RequestStatus`, `ResponseStatus`, `FeedbackCategory`

## 1-6. 예외 — `Exception` vs `Error`, Checked vs Unchecked

```
Throwable
├── Error            ← JVM 수준 치명적 문제. 잡지 말고, 던지지도 말 것.
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   └── IllegalAccessError    ← ⚠️ 이 프로젝트가 잘못 던지고 있는 것
└── Exception
    ├── IOException, SQLException ...        ← Checked: 반드시 try/catch 또는 throws
    └── RuntimeException                      ← Unchecked: 강제 안 됨
        ├── NullPointerException (NPE)
        ├── IllegalArgumentException
        └── ApplicationException             ← 이 프로젝트의 커스텀 예외 최상위
```

**Checked / Unchecked 구분이 중요한 이유 2가지**

1. 컴파일러가 `throws` 선언을 강제하는지 여부
2. **`@Transactional`의 롤백 기준이 여기서 갈립니다.**
   → `RuntimeException`, `Error`는 **롤백**. Checked Exception은 **커밋**. ([7-4](#7-4-롤백-규칙--checked-예외는-롤백되지-않는다))

**이 프로젝트의 예외 설계**

```java
// 1) 최상위: ErrorCode를 품은 RuntimeException
public class ApplicationException extends RuntimeException {
    private final ErrorCode errorCode;
    protected ApplicationException(ErrorCode errorCode) { this.errorCode = errorCode; }
}

// 2) 도메인별 구체 예외 — 생성자에 인자가 없다
public class BoardNotFoundException extends ApplicationException {
    private static final ErrorCode ERROR_CODE = ErrorCode.BOARD_NOT_FOUND;
    public BoardNotFoundException() { super(ERROR_CODE); }
}

// 3) 사용처 — 메서드 참조로 깔끔하게
boardRepository.findById(id).orElseThrow(BoardNotFoundException::new);
```

이 구조의 장점: **던지는 쪽은 HTTP 상태 코드를 몰라도 됩니다.**
`GlobalExceptionRestAdvice`가 `e.getErrorCode().getHttpStatus()`를 읽어 알아서 응답합니다.

## 1-7. `Optional<T>` — "값이 없을 수 있음"을 타입으로 표현

`null`을 반환하면 호출자가 `null` 체크를 잊고 NPE를 맞습니다.
`Optional`은 **컴파일 타임에 "너 이거 안 꺼냈어"** 라고 알려줍니다.

```java
Optional<Member> found = memberRepository.findByMemberBaseEmail(email);

found.orElseThrow(UserNotFoundException::new);   // 없으면 예외
found.map(PrincipalDetails::new);                 // 있으면 변환, 없으면 빈 Optional
found.orElse(null);                               // 없으면 null (이 프로젝트도 종종 씀)
found.isEmpty() / found.isPresent();
```

Spring Data JPA의 `findById`, `findBy…`는 관례적으로 `Optional`을 반환합니다.

## 1-8. 람다와 스트림

```java
// 스트림 3단 구성: 만들기 → 중간연산 → 최종연산
List<PointResponseDto> dtos = points.stream()          // 만들기
        .map(point -> PointResponseDto.fromEntity(point))  // 중간: 변환
        .collect(Collectors.toList());                      // 최종: 리스트로

// 메서드 참조 — 위 map과 동일한 의미의 축약형
.map(PointResponseDto::fromEntity)

// 필터 + 중복 제거 트릭 (RecruitmentService의 실제 코드)
Set<String> seen = new HashSet<>();
list.stream()
    .filter(r -> seen.add(r.getLink()))   // add()는 새로 넣었을 때만 true → 중복 제거
    .collect(Collectors.toList());
```

`Set.add()`가 중복 시 `false`를 반환하는 성질을 이용한 관용구입니다. 알아두면 코드가 읽힙니다.

# 2. 어노테이션이란 무엇인가

**어노테이션은 그 자체로 아무 동작도 하지 않습니다.** 코드에 붙이는 **메모(메타데이터)** 입니다.

```java
@Transactional          // ← 이 줄은 "이 메서드는 트랜잭션이 필요해요"라는 메모일 뿐
public void createBoard() { ... }
```

동작은 **그 메모를 읽는 누군가**가 만듭니다. 읽는 시점에 따라 두 종류로 나뉩니다.

| 시점 | 읽는 주체 | 예시 | 결과물 |
|---|---|---|---|
| **컴파일 타임** | 애노테이션 프로세서 | Lombok `@Getter`, `@Builder` | 컴파일된 `.class`에 코드가 실제로 생성됨 |
| **런타임** | 프레임워크 (리플렉션) | Spring `@Service`, `@Transactional`, JPA `@Entity` | 프레임워크가 스캔해서 객체를 만들고 감쌈 |

이 구분이 중요한 이유:

- Lombok은 컴파일이 끝나면 **흔적이 사라집니다**. `@Getter`가 만든 `getId()`는 그냥 평범한 메서드입니다.
- Spring 어노테이션은 **런타임에 계속 살아 있습니다**. 그래서 프록시니 리플렉션이니 하는 제약이 따라옵니다.
  → `private`에 붙인 `@Transactional`이 무시되는 이유가 여기서 나옵니다.

# 3. Lombok — 이 프로젝트가 가장 많이 쓰는 어노테이션들

## 3-1. 생성자 계열

```java
@RequiredArgsConstructor    // final 필드 + @NonNull 필드를 받는 생성자 생성
@Service
public class BoardService {
    private final BoardRepository boardRepository;   // 이 둘을 받는
    private final PointService pointService;          // 생성자가 자동 생성됨
}
```

생성되는 코드:

```java
public BoardService(BoardRepository boardRepository, PointService pointService) {
    this.boardRepository = boardRepository;
    this.pointService = pointService;
}
```

Spring은 **생성자가 하나면 `@Autowired` 없이도 자동으로 주입**합니다.
그래서 `@RequiredArgsConstructor` + `final` 필드 조합이 **생성자 주입의 표준 관용구**입니다.
([4-3](#4-3-의존성-주입di--왜-생성자-주입인가)에서 왜 이 방식이 좋은지 설명)

```java
@NoArgsConstructor(access = AccessLevel.PROTECTED)   // 파라미터 없는 생성자, 단 protected
@Entity
public class Member { ... }
```

**왜 `protected`인가?** JPA는 프록시를 만들 때 기본 생성자가 **반드시** 필요합니다(그래서 만들어줘야 함).
하지만 `public`으로 두면 개발자가 `new Member()`로 빈 껍데기를 만들 수 있어 위험합니다.
`protected`는 **JPA(같은 패키지 아닌 하이버네이트도 리플렉션으로 접근 가능)에게는 열어주고,
일반 코드에서는 막는** 절충안입니다.

## 3-2. `@Builder` — 인자 순서 실수를 없애는 생성 패턴

```java
Point newPoint = Point.builder()
        .member(member)
        .amount(-5)
        .type(PointType.QUESTION)
        .depositSum(newDepositSum)
        .withdrawSum(newWithdrawSum)
        .version(nextVersion)
        .build();
```

생성자 `new Point(member, -5, QUESTION, 100, -20, 3)`과 비교해보세요.
정수 인자 3개가 나란히 있으면 순서를 바꿔 넣어도 **컴파일 에러가 안 납니다.**
빌더는 이름을 강제하므로 이 사고를 막습니다. 필드가 4개 이상이면 빌더가 유리합니다.

## 3-3. `@Getter` — 그리고 `@Setter`가 없는 이유

이 프로젝트의 엔티티에는 `@Getter`만 있고 `@Setter`가 없습니다. 의도된 설계입니다.

```java
@Getter
@Entity
public class Member extends BaseTimeEntity {
    private int points;

    public void changePoint(int points) { this.points = points; }   // 의미 있는 이름의 변경 메서드
    public void changeTier(PointTier currentTier) { this.currentTier = currentTier; }
}
```

`setPoints(100)`은 "왜 바꾸는지"를 말해주지 않습니다.
`changePoint(100)`, `softDelete()`, `plusviewCount()`처럼 **행위 이름을 가진 메서드만 열어두면**
엔티티가 자기 상태 변화를 통제할 수 있습니다. 이걸 **응집도 있는 엔티티**라고 부릅니다.

## 3-4. `@Slf4j` — 로거 자동 생성

```java
@Slf4j
public class BoardService {
    // private static final Logger log = LoggerFactory.getLogger(BoardService.class);
    // ↑ 이 줄이 자동 생성됨. 그래서 바로 log.info(...) 사용 가능
}
```

```java
log.info("Cache HIT - Key: {}", cacheKey);            // {} 는 파라미터 자리
log.warn("캐시 조회 실패: {}", e.getMessage(), e);      // 마지막 인자로 예외를 넘기면 스택트레이스 출력
```

**`{}` 방식을 쓰는 이유**: `log.debug("값: " + heavyToString())`은 로그 레벨이 INFO여서
출력되지 않아도 **문자열 연결은 이미 수행됩니다**. `{}`를 쓰면 실제 출력이 필요할 때만 조립합니다.

# 4. Spring 핵심 — 빈, DI, 그리고 프록시

## 4-1. IoC(제어의 역전)와 빈(Bean)

객체를 **내가 `new`로 만드는 것**이 아니라 **스프링이 만들어 보관**하고, 필요한 곳에 넣어줍니다.
스프링이 관리하는 이 객체를 **빈(Bean)** 이라 하고, 보관소를 **애플리케이션 컨텍스트**라 합니다.

```
new BoardService(new BoardRepository(...), new PointService(...))   ← 내가 다 조립 (지옥)
                              ↓
스프링이 조립해서 컨테이너에 보관 → 필요한 곳에 주입                  ← IoC
```

## 4-2. 빈으로 등록하는 방법 2가지

**① 클래스에 스테레오타입 어노테이션을 붙인다** (컴포넌트 스캔이 찾아냄)

| 어노테이션 | 의미 | 기능 차이 |
|---|---|---|
| `@Component` | 일반 빈 | 기본형 |
| `@Service` | 비즈니스 로직 계층 | **기능은 `@Component`와 동일**, 의도 표현용 |
| `@Repository` | 데이터 접근 계층 | + DB 예외를 스프링 `DataAccessException`으로 변환 |
| `@Controller` / `@RestController` | 웹 요청 처리 | + 요청 매핑 대상이 됨 |
| `@Configuration` | 설정 클래스 | + 내부 `@Bean` 메서드를 처리 |

> `@SpringBootApplication`이 붙은 `MorningstarApplication`의 **패키지 아래만** 스캔합니다.
> 그래서 모든 코드가 `com.gaebang.backend` 아래에 있습니다.

**② `@Configuration` 클래스에서 `@Bean` 메서드로 직접 만든다** — **내가 만든 클래스가 아닐 때** 씁니다.

```java
@Configuration
public class AppConfig {
    @Bean
    public BCryptPasswordEncoder bCryptPasswordEncoder() {
        return new BCryptPasswordEncoder();   // 라이브러리 클래스라 @Component를 붙일 수 없다
    }
}
```

`@Bean` 메서드의 **반환 타입이 빈의 타입**, **메서드 이름이 빈의 이름**이 됩니다.

## 4-3. 의존성 주입(DI) — 왜 생성자 주입인가

```java
// ✅ 생성자 주입 (이 프로젝트의 표준)
@RequiredArgsConstructor
public class BoardService {
    private final BoardRepository boardRepository;
}

// ❌ 필드 주입 (지양)
public class BoardService {
    @Autowired private BoardRepository boardRepository;
}
```

생성자 주입의 이점:

1. **`final`을 쓸 수 있다** → 주입 후 절대 바뀌지 않음이 보장됨
2. **누락을 즉시 안다** → 주입할 빈이 없으면 애플리케이션이 **기동 자체를 실패**합니다.
   필드 주입은 기동은 되고 실제 호출 시 NPE가 납니다.
3. **순환 참조를 기동 시점에 잡는다**
4. **테스트에서 `new`로 직접 만들 수 있다** → 스프링 없이 단위 테스트 가능

> 이 프로젝트 `AuthConfig`에는 필드 주입(`@Autowired private PasswordEncoder passwordEncoder;`)과
> `@Bean passwordEncoder()`가 섞여 있어 혼란스러운 구조가 있습니다. → [global 문서](global.md)

## 4-4. 프록시 — Spring "마법"의 정체

**이 절이 이 문서에서 가장 중요합니다.**

`@Transactional`은 어떻게 트랜잭션을 시작하고 끝낼까요? 답: **스프링이 내 클래스를 상속한
자식 클래스를 런타임에 몰래 만들어서, 그 자식을 빈으로 등록합니다.** 이것이 **프록시(Proxy)** 입니다.

```
내가 만든 클래스                스프링이 만든 프록시 (CGLIB이 런타임에 생성)
┌──────────────────┐         ┌────────────────────────────────────┐
│ PointService     │         │ PointService$$SpringCGLIB$$0        │
│                  │ ◀────── │  extends PointService               │
│ createPoint()    │  상속    │                                     │
│                  │         │  @Override createPoint() {          │
└──────────────────┘         │      tx.begin();          ← 추가!   │
                             │      super.createPoint(); ← 원본    │
   ↑ 실제 빈은 이쪽이 아니라   │      tx.commit();         ← 추가!   │
     오른쪽 프록시입니다        │  }                                  │
                             └────────────────────────────────────┘
```

여기서 **세 가지 제약**이 자동으로 따라옵니다.

### 제약 ① `private` 메서드에는 적용되지 않는다

오버라이드는 **상속 가능한 메서드**에만 됩니다. `private`은 자식이 볼 수 없으므로 오버라이드 불가.
`final`, `static` 메서드도 같은 이유로 안 됩니다.

```java
@Transactional                 // ⚠️ 완전히 무시됨. 경고도 에러도 없음.
private PointResponseDto createPointInternal(...) { ... }
```

### 제약 ② 같은 클래스 안에서 호출하면(self-invocation) 적용되지 않는다

```java
public class PointService {
    public void createPoint() {
        createPointInternal();   // ⚠️ 이건 this.createPointInternal() — 프록시를 거치지 않음
    }

    @Transactional
    public void createPointInternal() { ... }   // public으로 바꿔도 여전히 무시됨!
}
```

프록시는 **바깥에서 들어오는 호출**만 가로챌 수 있습니다. 이미 원본 객체 안으로 들어온 뒤의
`this.xxx()` 호출은 프록시를 지나가지 않습니다.

**해결책**

```java
// 방법 A (권장): 트랜잭션 단위를 별도 빈으로 분리 — 호출이 프록시를 거치게 됨
@Service @RequiredArgsConstructor
public class PointService {
    private final PointTransactionService pointTransactionService;  // 다른 빈 → 프록시 경유 ✅
    public void createPoint() { pointTransactionService.create(...); }
}

// 방법 B: TransactionTemplate로 코드로 직접 트랜잭션 경계 지정
transactionTemplate.execute(status -> { ... });
```

### 제약 ③ 프록시 대상 메서드는 `public`이어야 한다

정리하면 — **`@Transactional`, `@Async`, `@Cacheable`, `@Retryable`, `@PreAuthorize` 등
모든 AOP 기반 어노테이션은 "public + 다른 빈에서 호출" 조건을 만족해야 동작합니다.**

## 4-5. `@Value` — 설정 파일 값 주입

```java
@Value("${moderation.async.core-pool-size:5}")
private int moderationCorePoolSize;
//        ↑ 프로퍼티 키      ↑ 콜론 뒤는 기본값 (키가 없으면 5)
```

`application.yml`의 값을 필드에 꽂아줍니다. 기본값을 주면 설정 누락 시 기동 실패를 피할 수 있습니다.

## 4-6. 프로필(Profile) — 환경별 설정 분리

```
application.yml         ← 공통 + 어떤 프로필을 켤지 결정 (active: dev)
application-core.yml    ← 항상 포함되는 공통 설정 (include: core)
application-dev.yml     ← 로컬 개발용 (localhost DB)
application-prod.yml    ← 운영용 (환경변수로 DB 주소 주입)
```

`spring.config.activate.on-profile: prod`는 "이 파일은 prod일 때만 유효"라는 선언입니다.

## 4-7. 비동기 · 스케줄 · 이벤트

```java
@EnableAsync        // @Async 활성화 (AsyncConfig에 있음)
@EnableScheduling   // @Scheduled 활성화 (MorningstarApplication에 있음)
```

```java
@Async("moderationExecutor")     // 지정한 스레드풀에서 별도 스레드로 실행 → 호출자는 즉시 리턴
public void moderateAsync(Long boardId) { ... }

@Scheduled(cron = "0 */10 * * * *", zone = "Asia/Seoul")   // 10분마다
public void fetchAndSaveRecruitment() { ... }
```

**cron 6자리 = `초 분 시 일 월 요일`** (표준 Unix cron은 5자리, 스프링은 초가 앞에 붙습니다)
`0 */10 * * * *` → 매시 0·10·20·30·40·50분의 0초에 실행.

```java
// 이벤트 발행/수신 — 발행자와 수신자를 서로 모르게 만든다 (느슨한 결합)
eventPublisher.publishEvent(new BoardCreatedEvent(saveBoard.getId()));

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(BoardCreatedEvent event) { ... }   // 커밋된 뒤에만 실행
```

> `@EventListener`는 **같은 트랜잭션 안에서 즉시(동기)** 실행됩니다.
> `@TransactionalEventListener(AFTER_COMMIT)`는 **커밋 후** 실행됩니다.
> "게시글 저장이 확정된 뒤에 AI 검열을 돌린다" 같은 요구사항은 후자가 맞습니다. → [community 문서](domain/community.md)

# 5. Spring MVC — 요청 하나가 지나가는 길

```
[클라이언트]
    │  POST /api/boards  + Authorization: Bearer eyJ...
    ▼
┌─────────────────────────────────────────────────────────┐
│ 1. 서블릿 필터 체인 (Servlet Filter)                      │
│    - JwtAuthenticationFilter   (로그인 시도 처리)          │
│    - JwtAuthorizationFilter    (토큰 검증 → SecurityContext)│
│    - Spring Security 인가 검사  (permitAll / authenticated) │
│                                                          │
│    ⚠️ 여기서 터진 예외는 @RestControllerAdvice가 못 잡습니다  │
│       (아직 DispatcherServlet에 도달하지 않았으므로)         │
└─────────────────────────────────────────────────────────┘
    ▼
┌─────────────────────────────────────────────────────────┐
│ 2. DispatcherServlet — 여기서부터 Spring MVC 영역          │
│    HandlerMapping으로 어느 컨트롤러 메서드인지 찾음          │
└─────────────────────────────────────────────────────────┘
    ▼
┌─────────────────────────────────────────────────────────┐
│ 3. 인자 바인딩 + 검증                                     │
│    @RequestBody → JSON을 DTO로 (Jackson)                 │
│    @Valid       → 실패 시 MethodArgumentNotValidException │
│    @AuthenticationPrincipal → SecurityContext에서 꺼냄    │
└─────────────────────────────────────────────────────────┘
    ▼
  Controller → Service (@Transactional 프록시!) → Repository → DB
    ▼
┌─────────────────────────────────────────────────────────┐
│ 4. 예외 발생 시 @RestControllerAdvice가 가로채 JSON 응답    │
│ 5. 반환 객체를 Jackson이 JSON으로 직렬화                    │
└─────────────────────────────────────────────────────────┘
```

**1번과 4번의 경계가 이 프로젝트의 실제 버그 지점입니다.**
`JwtAuthorizationFilter`에서 만료 토큰 파싱 시 `JwtException`이 터지는데 try/catch가 없어서,
`GlobalExceptionRestAdvice`가 잡지 못하고 **401이 아니라 500**이 나갑니다. → [global 문서](global.md)

## 5-1. 요청 매핑 어노테이션

```java
@RestController                      // @Controller + @ResponseBody
@RequestMapping("/api")              // 클래스 공통 접두 경로
public class BoardController {

    @GetMapping("/boards/{boardId}")                 // GET /api/boards/3
    public ResponseEntity<...> getBoardDetail(
        @PathVariable("boardId") Long boardId,       // 경로의 {boardId}
        @RequestParam("condition") String condition, // ?condition=xxx 쿼리스트링
        Pageable pageable,                            // ?page=0&size=10&sort=createdAt,DESC 자동 바인딩
        @RequestBody BoardCreateAndEditRequestDto dto, // 요청 본문 JSON → DTO
        @AuthenticationPrincipal PrincipalDetails principalDetails  // 로그인 사용자
    ) { ... }
}
```

- `@RestController` = `@Controller` + `@ResponseBody`.
  `@ResponseBody`가 있으면 반환값을 **뷰 이름이 아니라 응답 본문(JSON)** 으로 처리합니다.
- `Pageable`은 스프링이 쿼리 파라미터에서 자동 조립합니다. 기본 size는 20입니다.
- **`@AuthenticationPrincipal`은 인증이 없으면 `null`을 넣습니다.**
  그래서 `permitAll`로 열어둔 엔드포인트에서 `principalDetails.getMember()`를 하면 **NPE → 500**입니다.
  이 프로젝트에 이 문제가 여러 개 있습니다. → [global 문서](global.md)

## 5-2. `ResponseEntity`와 이 프로젝트의 응답 규약

```java
ResponseDTO<Page<BoardListResponseDto>> body = ResponseDTO.okWithData(boardDto);
return ResponseEntity.status(body.getCode()).body(body);
```

`ResponseEntity`는 **상태 코드 + 헤더 + 본문**을 모두 제어하는 반환 타입입니다.
이 프로젝트는 본문 안에도 `code`를 한 번 더 넣는 규약(`ResponseDTO`)을 씁니다.

```json
{ "code": 200, "message": "요청이 성공적으로 처리되었습니다.", "data": { ... } }
```

`ObjectMapper`에 `NON_NULL`을 걸어두었으므로 `data`가 없으면 그 필드는 JSON에서 빠집니다.

## 5-3. `@Valid` — 검증은 DTO에 선언한다

```java
public record StartSessionRequestDto(
    @NotNull(message = "직무를 선택해주세요") JobRole role,
    @Size(max = 2000) String profileSnapshot
) { }

@PostMapping("/session")
public ... start(@Valid @RequestBody StartSessionRequestDto req) { ... }
```

`@Valid`가 붙어야 검증이 **실행**됩니다. 붙이지 않으면 DTO의 `@NotNull`은 장식입니다.
실패하면 `MethodArgumentNotValidException` → `GlobalExceptionRestAdvice`가 400으로 변환합니다.

# 6. JPA — 이 문서의 심장

## 6-1. 세 층의 이름 정리

| 이름 | 정체 |
|---|---|
| **JPA** | 자바 표준 **명세(인터페이스)**. `jakarta.persistence.*` 패키지. 구현체가 아니다. |
| **Hibernate** | JPA 명세의 **구현체**. 실제로 SQL을 만들고 실행하는 엔진. |
| **Spring Data JPA** | Hibernate를 **더 편하게 쓰게 해주는 스프링 모듈**. `JpaRepository` 인터페이스가 여기 것. |

`build.gradle`의 `spring-boot-starter-data-jpa` 하나가 이 셋 + HikariCP 커넥션 풀을 다 가져옵니다.

```java
import jakarta.persistence.*;          // ← JPA 표준 (@Entity, @Id, @Column ...)
import org.springframework.data.jpa.*; // ← Spring Data JPA
import org.hibernate.*;                // ← Hibernate 고유 기능 (직접 쓸 일은 드묾)
```

## 6-2. 엔티티 매핑 어노테이션

```java
@Entity                                     // "이 클래스는 DB 테이블과 매핑됩니다"
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Table(name = "points", uniqueConstraints = {                 // 테이블명 + 제약조건
        @UniqueConstraint(columnNames = {"member_id", "version"})
})
public class Point extends BaseTimeEntity {

    @Id                                                        // primary key
    @GeneratedValue(strategy = GenerationType.IDENTITY)        // PK 생성 전략
    @Column(name = "point_id")                                 // 컬럼명 지정
    private Long pointId;

    @ManyToOne(fetch = FetchType.LAZY)                         // N:1 관계
    @JoinColumn(name = "member_id", nullable = false)          // FK 컬럼
    private Member member;

    @Enumerated(EnumType.STRING)                               // enum을 문자열로 저장
    @Column(nullable = false, length = 20)
    private PointType type;

    @Column(name = "deposit_sum", nullable = false)
    private Integer depositSum;
}
```

### `@GeneratedValue` 전략

| 전략 | 동작 | 특징 |
|---|---|---|
| `IDENTITY` | DB의 AUTO_INCREMENT에 맡김 | **이 프로젝트가 쓰는 방식.** MySQL 표준. |
| `SEQUENCE` | DB 시퀀스 객체 사용 | Oracle, PostgreSQL |
| `TABLE` | 키 관리용 테이블 사용 | 느림, 거의 안 씀 |
| `AUTO` | 방언에 따라 자동 선택 | 예측하기 어려워 명시 권장 |

> **IDENTITY의 중요한 부작용**: ID를 DB가 만들어주므로, `persist()` 시점에 **INSERT를 즉시 실행**해야
> ID를 알 수 있습니다. 그래서 IDENTITY는 **쓰기 지연(batch insert) 최적화가 불가능**합니다.
> 반복문에서 `save()`를 100번 호출하면 INSERT가 100번 즉시 나갑니다.
> → 이 프로젝트 `BoardService.createBoard`의 `images.forEach(... imageRepository.save(...))`가 그 예입니다.

### `@Enumerated(EnumType.STRING)`을 반드시 쓸 것

```java
@Enumerated(EnumType.STRING)    // ✅ DB에 "QUESTION" 문자열로 저장
@Enumerated(EnumType.ORDINAL)   // ❌ 기본값! enum 선언 순서(0,1,2)를 숫자로 저장
```

`ORDINAL`은 **enum 중간에 상수를 하나 추가하면 기존 데이터의 의미가 전부 밀립니다.**
`@Enumerated`를 아예 생략하면 `ORDINAL`이 기본값이라 더 위험합니다. 항상 `STRING`을 명시하세요.
이 프로젝트는 잘 지키고 있습니다.

### `@MappedSuperclass` — 테이블 없는 공통 필드 묶음

```java
@Getter
@MappedSuperclass                                  // 테이블이 생기지 않는다. 필드만 물려준다.
@EntityListeners(AuditingEntityListener.class)     // 생명주기 이벤트를 감시할 리스너 지정
public abstract class BaseTimeEntity {
    @CreatedDate       protected LocalDateTime createdAt;    // INSERT 시 자동 채움
    @LastModifiedDate  protected LocalDateTime updatedAt;    // UPDATE 시 자동 갱신
}
```

이게 동작하려면 **`@EnableJpaAuditing`이 켜져 있어야 합니다.** 이 프로젝트는 `JpaConfig`에 있습니다.

```java
@Configuration
@EnableJpaAuditing      // 이게 없으면 createdAt이 계속 null로 들어갑니다
public class JpaConfig { }
```

> `@MappedSuperclass` vs `@Entity` 상속: 전자는 **테이블이 안 생기고 필드만 자식 테이블에 합쳐집니다.**
> 후자(`@Inheritance`)는 실제 테이블 상속 전략이라 완전히 다른 이야기입니다.

### `@Embedded` / `@Embeddable` — 값 타입 묶기

```java
@Entity
public class Member {
    @Embedded
    protected MemberBase memberBase;   // email, nickname, password, authority를 한 덩어리로
}
```

`MemberBase`의 필드들이 **`member` 테이블의 컬럼으로 그대로 들어갑니다** (별도 테이블 아님).
"이메일·닉네임·비번·권한은 회원의 신원 정보"라는 개념적 묶음을 코드로 표현한 것입니다.
꺼낼 때 `member.getMemberBase().getEmail()`처럼 한 단계 더 들어가야 하는 건 이 설계의 비용입니다.

## 6-3. 영속성 컨텍스트 — JPA를 이해하는 열쇠

**영속성 컨텍스트(Persistence Context)** 는 "엔티티를 보관하는 1차 캐시"입니다.
`EntityManager`가 이걸 관리하고, **트랜잭션 범위와 생명주기가 같습니다.**

```
트랜잭션 시작 ─────────────────────────────────── 커밋
     │                                            │
     │  ┌─────── 영속성 컨텍스트 ──────────┐        │
     │  │ @Id=1 → Member(points=100)      │        │
     │  │ @Id=3 → Board(viewCount=5)      │        │
     │  └──────────────────────────────────┘        │
     │                                            ▼
     └── 이 안에 있는 동안 = "영속 상태"        flush → SQL 실행
```

### 엔티티의 4가지 상태

```java
// 1) 비영속 (new/transient) — 그냥 자바 객체. JPA가 모른다.
Board board = Board.builder().title("제목").build();

// 2) 영속 (managed) — 영속성 컨텍스트가 관리 중. 변경을 추적한다.
boardRepository.save(board);          // 또는 findById로 조회한 엔티티

// 3) 준영속 (detached) — 관리에서 떨어져 나온 상태. 변경을 추적하지 않는다.
//    → 트랜잭션이 끝나면 모든 엔티티가 이 상태가 됩니다.

// 4) 삭제 (removed)
boardRepository.delete(board);
```

**"준영속"이 왜 중요한가**: 트랜잭션 없이 조회한 엔티티는 곧바로 준영속이 되고,
그 뒤에 값을 바꿔도 **DB에 아무 일도 일어나지 않습니다.**
이 프로젝트 `PointService`의 버그가 정확히 이것입니다. ([7-6](#7-6-이-프로젝트의-실제-사례--pointservice))

## 6-4. 더티 체킹 — `save()` 없이 UPDATE가 되는 이유

가장 처음 헷갈리는 지점입니다.

```java
@Transactional
public void editBoard(Long boardId, BoardCreateAndEditRequestDto dto, ...) {
    Board findBoard = boardRepository.findByIdAndMemberId(boardId, memberId)
            .orElseThrow(BoardNotFoundException::new);

    findBoard.updateBoard(dto);        // ← 자바 객체의 필드만 바꿨다

    boardRepository.save(findBoard);   // ← 이 줄은 사실 없어도 UPDATE가 나갑니다
}
```

**동작 원리**

1. 조회 시점에 JPA가 엔티티의 **스냅샷(원본 복사본)** 을 떠둡니다.
2. 트랜잭션 커밋 직전 `flush()`가 일어날 때, **현재 값과 스냅샷을 필드별로 비교**합니다.
3. 달라진 필드가 있으면 **UPDATE SQL을 자동 생성**합니다.

이것이 **더티 체킹(Dirty Checking)** 입니다. 그래서:

> **영속 상태 엔티티는 `save()`를 호출하지 않아도 변경이 반영됩니다.**
> `plusviewCount()`, `changePoint()`, `softDelete()` 같은 메서드만 호출하면 끝입니다.

`save()`가 필요한 경우는 **새 엔티티를 INSERT할 때**뿐입니다.

### `save()`의 실제 구현

```java
// Spring Data JPA — SimpleJpaRepository
@Transactional
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {   // @Id가 null이면 새 엔티티로 판단
        em.persist(entity);                   // INSERT
        return entity;
    } else {
        return em.merge(entity);              // 준영속 엔티티를 다시 영속화 (SELECT 후 UPDATE)
    }
}
```

**`merge()`의 함정**: `merge`는 **넘긴 객체를 영속화하지 않습니다.**
DB에서 다시 읽어 새 영속 객체를 만들고 값을 복사한 뒤 **그 새 객체를 반환**합니다.
그래서 `merge`를 쓸 때는 반드시 반환값을 받아 써야 합니다. 게다가 `merge`는
**모든 필드를 덮어쓰므로** 일부만 채운 객체를 넘기면 나머지가 `null`로 밀립니다.
→ 그래서 "**조회해서 필드만 바꾸는**" 더티 체킹 방식이 권장됩니다.

## 6-5. `flush`와 `commit`의 차이

| | 하는 일 |
|---|---|
| `flush()` | 영속성 컨텍스트의 변경을 **SQL로 DB에 전송**. 트랜잭션은 계속 열려 있음. |
| `commit()` | 트랜잭션 확정. 내부적으로 `flush()`를 먼저 호출한 뒤 커밋. |

flush가 자동으로 일어나는 시점:
1. 트랜잭션 커밋 직전
2. JPQL 쿼리 실행 직전 (아직 안 보낸 변경이 쿼리 결과에 반영되어야 하므로)
3. `em.flush()` 직접 호출

## 6-6. 연관관계와 지연 로딩(LAZY)

```java
@ManyToOne(fetch = FetchType.LAZY)      // Point 여러 개 : Member 하나
@JoinColumn(name = "member_id")         // points 테이블에 member_id FK 컬럼이 생긴다
private Member member;
```

- **`@ManyToOne`의 기본값은 `EAGER`(즉시 로딩)** 입니다. **반드시 `LAZY`로 바꿔야 합니다.**
  EAGER면 Point를 조회할 때마다 Member를 JOIN하거나 추가 SELECT를 날립니다.
- `@OneToMany`의 기본값은 이미 `LAZY`입니다.

**LAZY의 동작**: `point.getMember()`를 호출하는 그 순간에 SELECT가 나갑니다.
그전까지는 `Member` 자리에 **프록시(가짜 객체)** 가 들어있습니다.

```java
Point point = pointRepository.findById(1L).get();   // SELECT * FROM points WHERE point_id=1
Long id = point.getMember().getId();                 // FK 값이라 프록시로 해결 → 쿼리 안 나감
String email = point.getMember().getMemberBase().getEmail();  // 여기서 SELECT * FROM member
```

⚠️ **`LazyInitializationException`**: 프록시를 초기화하려면 영속성 컨텍스트가 살아 있어야 합니다.
트랜잭션이 끝난 뒤(예: 컨트롤러나 뷰에서) LAZY 필드를 처음 건드리면 이 예외가 납니다.

```yaml
spring.jpa.open-in-view: false    # 이 프로젝트 prod 설정 — 올바른 선택
```

`open-in-view: true`(스프링 부트 기본값)는 **HTTP 응답이 끝날 때까지 영속성 컨텍스트를 열어둡니다.**
편하지만 DB 커넥션을 오래 붙잡아 성능이 나빠집니다. `false`로 끄고
**서비스 계층 안에서 필요한 데이터를 모두 DTO로 변환**하는 것이 정석입니다.
이 프로젝트가 `fromEntity(...)`를 서비스에서 호출하는 이유가 이것입니다.

## 6-7. N+1 문제 — 그리고 이 프로젝트의 대응

```java
List<Board> boards = boardRepository.findAll();     // ① SELECT * FROM board  (1번)
for (Board b : boards) {
    b.getMember().getMemberBase().getNickname();     // ② 게시글마다 SELECT member (N번)
}
// 총 1 + N 번의 쿼리 → N+1 문제
```

**해결 방법**

```java
// 방법 1) fetch join — 한 번에 JOIN해서 가져온다
@Query("SELECT b FROM Board b JOIN FETCH b.member WHERE b.id = :id")
Optional<Board> findBoardDetailById(@Param("id") Long id);

// 방법 2) 프로젝션 DTO — 필요한 컬럼만 골라 DTO로 바로 받는다 (엔티티를 아예 안 만든다)
@Query("""
    SELECT new com.gaebang.backend...BoardListProjectionDto(b.id, b.title, m.memberBase.nickname, ...)
    FROM Board b JOIN b.member m
    """)
Page<BoardListProjectionDto> findAllBoardDtos(Pageable pageable);

// 방법 3) IN 절 벌크 조회 — 반복 조회를 한 방으로
List<String> existingLinks = recruitmentRepository.findExistingLinks(links);
```

이 프로젝트는 세 방법을 모두 쓰고 있습니다. (`BoardListProjectionDto`, `findBoardDetailById`,
`findExistingLinks`) → [community](domain/community.md), [recruitmentNotice](domain/recruitmentNotice.md)

## 6-8. Spring Data JPA 리포지토리 — 인터페이스만 쓰면 끝

```java
public interface BoardRepository extends JpaRepository<Board, Long> {
    //                                                 ↑엔티티  ↑PK타입

    // ① 쿼리 메서드 — 메서드 이름을 파싱해서 스프링이 SQL을 만들어줍니다
    Optional<Board> findByIdAndMemberId(Long id, Long memberId);
    Long countByBoardIdAndDeleteYn(Long boardId, String deleteYn);

    // ② @Query — 복잡한 건 JPQL을 직접 씁니다
    @Query("SELECT b FROM Board b WHERE b.title LIKE %:cond%")
    Page<BoardListProjectionDto> findByCondition(@Param("cond") String cond, Pageable pageable);
}
```

**구현 클래스를 아무도 만들지 않았는데 동작합니다.** 스프링이 기동 시점에 이 인터페이스의
프록시 구현체를 만들어 빈으로 등록합니다. `@Repository`를 붙이지 않아도 됩니다.

**쿼리 메서드 키워드 사전**

| 키워드 | JPQL/SQL |
|---|---|
| `findBy`, `getBy`, `readBy` | SELECT |
| `countBy` | COUNT |
| `existsBy` | 존재 여부 → boolean |
| `deleteBy` | DELETE (⚠️ 엔티티를 하나씩 조회해 지웁니다) |
| `And`, `Or` | AND / OR |
| `After`, `Before`, `GreaterThan`, `LessThan` | 비교 |
| `Like`, `Containing`, `StartingWith` | LIKE |
| `OrderBy…Desc` | ORDER BY |
| `In` | IN |
| `_` (언더스코어) | 중첩 프로퍼티 경로 명시 (`findByMemberBase_Nickname`) |

이 프로젝트의 실제 예:
`findByExpirationDateAfterAndPubDateAfterOrderByPubDateDesc(now, twoMonthsAgo)`
→ `WHERE expiration_date > ? AND pub_date > ? ORDER BY pub_date DESC`

## 6-9. `ddl-auto` — 스키마를 누가 만드나

```yaml
spring.jpa.hibernate.ddl-auto: update
```

| 값 | 동작 |
|---|---|
| `none` | 아무것도 안 함 (**운영 권장**) |
| `validate` | 엔티티와 실제 스키마가 맞는지 검증만 |
| `update` | 부족한 테이블/컬럼을 **추가**. 삭제·타입변경은 **안 함** |
| `create` | 기동 시 drop 후 create |
| `create-drop` | 기동 시 create, 종료 시 drop |

> ⚠️ **이 프로젝트는 prod에서도 `update`입니다.** 컬럼을 지우거나 타입을 바꿔도 반영되지 않아
> 엔티티와 실제 스키마가 조용히 어긋납니다(스키마 드리프트). Flyway 같은 마이그레이션 도구로
> 옮기는 것이 정석입니다. (`resources/db/migration/`이 비어 있는 걸 보면 도입하려던 흔적은 있습니다.)

# 7. 트랜잭션 — `@Transactional`의 진짜 동작

## 7-1. 트랜잭션이란

여러 DB 작업을 **"전부 성공" 또는 "전부 실패"의 한 덩어리**로 묶는 것입니다.

```
포인트 5점 차감  ─┐
                  ├─ 둘 다 성공해야 의미가 있음. 하나만 되면 사용자가 손해를 봄.
질문 내용 저장   ─┘
```

## 7-2. `@Transactional`이 하는 일

```java
@Transactional
public void createBoard(...) { ... }
```

프록시가 이렇게 감쌉니다:

```java
try {
    tx = transactionManager.getTransaction();   // BEGIN
    target.createBoard(...);                     // 원본 실행
    transactionManager.commit(tx);               // COMMIT
} catch (RuntimeException | Error e) {
    transactionManager.rollback(tx);             // ROLLBACK
    throw e;
}
```

**즉 `@Transactional`은 프록시입니다.** [4-4](#4-4-프록시--spring-마법의-정체)의 세 제약이 전부 적용됩니다.

## 7-3. `readOnly = true` — 단순 최적화가 아니다

```java
@Transactional(readOnly = true)
public Page<BoardListResponseDto> getBoard(Pageable pageable) { ... }
```

세 가지 일이 벌어집니다:

1. Hibernate `FlushMode`가 `MANUAL`이 됩니다 → **커밋 시 자동 flush가 일어나지 않습니다**
2. 조회한 엔티티의 **스냅샷을 만들지 않습니다** → 더티 체킹 대상에서 제외 (메모리 절약)
3. JDBC 드라이버에 read-only 힌트를 전달합니다 (DB에 따라 읽기 전용 복제본으로 라우팅)

> ⚠️ **그래서 `readOnly = true` 안에서 엔티티를 변경하면 그 변경은 사라집니다.**
> 이 프로젝트 `BoardService.getBoardDetail`이 정확히 이 실수를 합니다:
>
> ```java
> @Transactional(readOnly = true)
> public BoardDetailResponseDto getBoardDetail(...) {
>     Board findBoard = boardRepository.findBoardDetailById(boardId).orElseThrow(...);
>     findBoard.plusviewCount();     // ⚠️ 조회수 증가가 DB에 반영되지 않습니다
>     ...
> }
> ```

## 7-4. 롤백 규칙 — Checked 예외는 롤백되지 않는다

```java
@Transactional
public void doSomething() throws IOException {
    repository.save(entity);
    throw new IOException("실패!");     // ⚠️ Checked 예외 → 커밋됩니다!
}
```

기본 규칙:

| 던진 것 | 결과 |
|---|---|
| `RuntimeException` 및 그 자손 | **롤백** |
| `Error` | **롤백** |
| Checked `Exception` (`IOException`, `Exception` …) | **커밋** |

Checked 예외에도 롤백하려면 명시해야 합니다:

```java
@Transactional(rollbackFor = Exception.class)
```

이 프로젝트가 커스텀 예외를 모두 `RuntimeException`(`ApplicationException`) 기반으로 만든 것은
이 규칙 때문에 **올바른 선택**입니다.

## 7-5. 전파(Propagation) — 트랜잭션 안에서 트랜잭션을 만나면

| 옵션 | 동작 |
|---|---|
| `REQUIRED` (기본) | 진행 중인 트랜잭션이 있으면 **참여**, 없으면 새로 시작 |
| `REQUIRES_NEW` | **항상 새 트랜잭션**을 시작 (기존 것은 잠시 보류) |
| `NESTED` | 세이브포인트 사용 |
| `SUPPORTS` / `NOT_SUPPORTED` / `MANDATORY` / `NEVER` | 특수 상황 |

**`REQUIRED`의 함정 — rollback-only 마킹**

```java
@Transactional                       // 트랜잭션 A 시작
public void outer() {
    try {
        inner();                     // 같은 트랜잭션 A에 참여
    } catch (Exception e) {
        // 예외를 잡아서 무시했다!
    }
    // ⚠️ 그래도 커밋 시점에 UnexpectedRollbackException이 터집니다
}

@Transactional
public void inner() { throw new RuntimeException(); }   // 트랜잭션 A를 rollback-only로 마킹
```

내부에서 예외가 나면 트랜잭션은 이미 **"롤백해야 함"으로 도장이 찍힙니다.**
바깥에서 예외를 삼켜도 되돌릴 수 없습니다. **재시도 로직을 트랜잭션 안에서 짜면 안 되는 이유**입니다.

## 7-6. 이 프로젝트의 실제 사례 — `PointService`

지금까지 배운 것이 전부 한 곳에 모여 있는 예입니다.

```java
// PointService.java
public PointResponseDto createPoint(PointRequestDto dto, PrincipalDetails principal) {
    int retryCount = 0;
    while (retryCount < 3) {
        try {
            return createPointInternal(dto, memberId);        // ← ①
        } catch (DataIntegrityViolationException | ObjectOptimisticLockingFailureException e) {
            retryCount++;                                     // ← ②
            Thread.sleep(50L * retryCount);
        }
    }
    throw new PointCreationRetryExhaustedException();
}

@Transactional                                                 // ← ③
private PointResponseDto createPointInternal(PointRequestDto dto, Long memberId) {
    Member member = memberRepository.findById(memberId).orElseThrow(UserNotFoundException::new);
    ...
    pointRepository.save(newPoint);
    member.changePoint(calculatedPoint);                        // ← ④ 더티 체킹에 의존
    updateMemberTierIfNeeded(member, calculatedPoint);
    return PointResponseDto.fromEntity(newPoint);
}
```

**세 개의 문제가 겹쳐 있습니다.**

| # | 문제 | 근거 |
|---|---|---|
| ③ | **`private` + self-invocation** → `@Transactional`이 완전히 무시됨 | [4-4](#4-4-프록시--spring-마법의-정체) |
| ④ | 트랜잭션 없이 호출되면 `member`가 **준영속** → `changePoint()` 결과가 **DB에 반영되지 않음** | [6-3](#6-3-영속성-컨텍스트--jpa를-이해하는-열쇠), [6-4](#6-4-더티-체킹--save-없이-update가-되는-이유) |
| ②  | 외부 트랜잭션(예: `BoardService.createBoard`) 안에서 호출되면 이미 **rollback-only** → 재시도해도 성공 불가 | [7-5](#7-5-전파propagation--트랜잭션-안에서-트랜잭션을-만나면) |

**의도한 대로 고치는 방법**

```java
// 트랜잭션 단위를 별도 빈으로 분리 + 시도마다 새 트랜잭션
@Service
@RequiredArgsConstructor
public class PointTransactionService {

    private final PointRepository pointRepository;
    private final MemberRepository memberRepository;
    private final PointTierService pointTierService;

    @Transactional(propagation = Propagation.REQUIRES_NEW)   // 시도마다 독립 트랜잭션 ✅
    public PointResponseDto create(PointRequestDto dto, Long memberId) { ... }
}

@Service
@RequiredArgsConstructor
public class PointService {
    private final PointTransactionService pointTransactionService;   // 다른 빈 → 프록시 경유 ✅

    public PointResponseDto createPoint(...) {
        for (int i = 0; i < 3; i++) {
            try { return pointTransactionService.create(dto, memberId); }
            catch (DataIntegrityViolationException | ObjectOptimisticLockingFailureException e) { ... }
        }
        throw new PointCreationRetryExhaustedException();
    }
}
```

자세한 배경은 [point 문서](domain/point.md)에서 다룹니다.

# 8. 이 프로젝트의 코딩 관용구

같은 패턴이 반복되므로 한 번만 익히면 나머지 도메인이 빠르게 읽힙니다.

## 8-1. 계층 구조

```
Controller  — HTTP만 안다. 검증 → 서비스 호출 → ResponseDTO로 감싸 반환
    ↓
Service     — 비즈니스 로직 + @Transactional 경계. 엔티티 ↔ DTO 변환도 여기서.
    ↓
Repository  — DB 접근만. 인터페이스 하나로 끝.
    ↓
Entity      — DB 테이블 매핑 + 자기 상태를 바꾸는 메서드
```

## 8-2. `fromEntity` / `toEntity` — 변환 메서드의 방향

```java
// 응답 DTO: 엔티티 → DTO  ⇒ 정적 팩토리 fromEntity
public record PointResponseDto(Long pointId, Integer amount, ...) {
    public static PointResponseDto fromEntity(Point point) {
        return new PointResponseDto(point.getPointId(), point.getAmount(), ...);
    }
}

// 요청 DTO: DTO → 엔티티  ⇒ toEntity
public record PointRequestDto(Integer amount, PointType type) {
    public Point toEntity(Member member, Integer depositSum, Integer withdrawSum, Integer version) {
        return Point.builder().member(member).amount(amount)...build();
    }
}
```

**왜 엔티티를 그대로 응답하지 않는가?**

1. 비밀번호 같은 **민감 필드가 새어 나갑니다**
2. LAZY 프록시를 Jackson이 직렬화하려다 `LazyInitializationException`이 납니다
3. 엔티티 필드명을 바꾸면 **API 스펙이 같이 깨집니다** (DB와 API가 강하게 결합)
4. 양방향 연관관계면 **무한 순환 참조**로 직렬화가 폭발합니다

## 8-3. Soft Delete — 지우지 않고 지운 척하기

```java
public void softDelete() { this.deleteYn = "Y"; }
```

물리 삭제(`DELETE`)를 하면 통계·감사·복구가 불가능해집니다. 그래서 플래그만 바꾸고
조회 시 `WHERE delete_yn = 'N'`으로 걸러냅니다. 이 프로젝트는 `Board`, `Comment`에 적용했습니다.

## 8-4. 이벤트 소싱풍 포인트 원장

`Point` 테이블은 잔액을 덮어쓰지 않고 **거래마다 새 행을 추가**합니다.

```
version | amount | deposit_sum | withdraw_sum | type
   1     |  +10   |     10      |      0       | BOARD
   2     |   -5   |     10      |     -5       | QUESTION
   3     | +10    |     20      |     -5       | FEEDBACK      → 현재 잔액 = 20 + (-5) = 15
```

`@UniqueConstraint(columnNames = {"member_id", "version"})`이 **같은 회원의 같은 버전이
두 번 생기는 것(동시 요청)을 DB 차원에서 막습니다.** 그래서 충돌 시
`DataIntegrityViolationException`이 나고, 그걸 잡아 재시도하는 구조입니다.
"통장 거래내역"과 같은 발상이고, 잔액 감사가 가능한 좋은 설계입니다.

## 8-5. 정적 팩토리 메서드 + `private` 생성자

```java
@Getter
public class ResponseDTO<T> {
    @Builder
    private ResponseDTO(int code, String message, T data) { ... }   // 생성자를 막고

    public static ResponseDTO<Void> ok() { ... }                    // 이름 있는 통로만 열어둔다
    public static <T> ResponseDTO<T> okWithData(T data) { ... }
    public static ResponseDTO<Void> error(ErrorCode errorCode) { ... }
}
```

생성자는 이름을 가질 수 없습니다. `ok()`, `error()`처럼 **이름으로 의도를 드러낼 수 있는 것**이
정적 팩토리 메서드의 장점입니다.
